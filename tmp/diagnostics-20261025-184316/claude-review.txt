# alt-henkan 0.4.3 入力異常 調査・対策案レビュー

レビューは読み取りのみで行いました（Read/Grep/Glob）。ビルド、テスト、probe はどれも実行していないため、`probe-result.txt` の結果も含めて実行結果は未確認です。

## 総括

- 内部状態が残ってからの経路は、ログとコードで裏付けられました。調査結果は概ね正確です。
- ただし、影響の重さを小さく書いている箇所が2点あります。
  - Ctrl を再送信した後は、Windows 上で Ctrl が実際に押されたままになり、通常の打鍵が Ctrl+キーとしてアプリに届いています。
  - その状態になると、提案の「Alt と同様のタイマー復旧」では検出できなくなります。
- 対策は、修飾キーの判定を変えるだけでは足りません。`ConsumePendingControlGesture` で古い Ctrl が「隠し保持」に変わる遷移を止めることが必須です。

## 重要度順の指摘

### 1.【高・確定】再送信後は Windows の Ctrl が自前注入で押されたままになり、タイマー復旧では検出できない

**根拠**
- seq51309〜51316: Ctrl down を再送信し、asyncRaw が 0 から 1、state が 0x34000D になります。
- その後、Emacs 処理の時だけ Ctrl up が送られ、次の入力で再び down が送られる、という往復が続きます（seq51332〜51359、51372〜51399、51530〜51573）。
- seq51399 から 51530 までの約40秒間は asyncRaw=0x1 のままです。その間に Other キーが通過し（例: seq51407）、クリックも発生し、前面プロセスは pid 29296／16504／14420 と切り替わっています。

**影響**
- Emacs 対象外の打鍵とクリックが、実際の Ctrl+キー／Ctrl+クリックとしてアプリに渡ったことになります。
- 調査では「Ctrl再送信」としか書かれておらず、この影響が入っていません。

**対策案1との関係**
- `AltReleaseMonitor.Observe` は AsyncDown が真だとリセットします（`AltModifierSnapshot.cs:24`）。
- そのため、自前の注入で down になった状態は「正当な長押し」と区別できず、復旧は永久に起きません。

**推奨**: 再送信に至る前の段階で止めることを主対策にし、タイマーは補助と位置づけます（指摘2）。

### 2.【高・確定】古い Ctrl が「隠し保持」に戻る経路は1つだけで、修飾キー判定の修正だけでは塞げない

**根拠**
- OriginalDownPassed／NativeDownSent を false に戻す処理は、`Start`、`Reset`、`ConsumePendingControlGesture`（`AltInputService.cs:697-698`）の3か所だけです。
- このうち Consume を通ると `HiddenFromForeground` が真になります（`:1244`）。すると `PromotePendingControlToNative` が再送信を許可します（`:591`）。
- `ConsumePendingControlGestures` は、Control 付きのバインディングが成立すると左右の両方を無条件に処理します（`:679-680`）。

**残る経路**
左 Ctrl だけを判定から外しても、次の場合には古い左 Ctrl が Consume されて隠し保持に変わり、復活します。
- 右 Ctrl を実際に押して Ctrl+F を入力した場合
- 他のツールが注入した Ctrl により `AsyncAnyDown`（VK_CONTROL、`:719`）が真になった場合

**推奨**
- Consume は、修飾判定に寄与した側だけを対象にします。
- NativeVisible なのに側別の async が up になっている状態は、隠し保持に変えず、up も送らずに残します。解除はタイマーに任せます。
- Promote は隠し状態だけを扱うので、Consume を塞げば変更は不要です。

### 3.【高・コード上確定、今回のログでは未発生】古い Ctrl が残っている間に Ctrl を押し直しても、Windows に届かない

**根拠**
- IsDown 中に届いた非自前の down は、NativeDownSent=true でも `ControlRepeat` として抑止されます（`:358-362`）。
- Alt の方は同じ問題を `AltRepeatNative` で修正済みです（`:442-449`）。Ctrl には同等の処理がありません。

**影響**
- Windows 側が up のまま利用者が Ctrl+C を押すと、C は Emacs 対象外として通過します。Promote は NativeDownSent=true なので何もしません。結果として、素の c が入力されることになります。
- 利用者が押し直して自分で直す、という手段が効きません。
- 今回の seq51581 で問題にならなかったのは、直前に再送信していて Windows 側がたまたま down だったためです。

**推奨**: Alt と同じ方式にします。NativeVisible 中に非自前の down が来たら通過させ、OriginalDownPassed=true、NativeDownSent=false とし、監視をリセットします。

### 4.【中・確定】Alt のタップ判定と IME 切替にも影響していた（調査に記載なし）

**根拠**
- 再送信中は `IsAnyNonAltKeyDown` が VK_CONTROL を真と見ます（`:633`）。
- そのため Alt は AltDeferred ではなく AltNative として通過していました（seq51364、51481、51493、51514、51522）。

**影響**
- この間、Alt のタップでは IME が切り替わりません。代わりに Ctrl+Alt がアプリに届きます。

### 5.【中・確定】今回の事例では、タイマー復旧があれば入力再開前に解除できていた

**根拠**
- 18:14:36 に Alt が、信頼できる読み取りという条件の下で復旧しています（通常ログ:148）。
- 同じ時点の asyncCtrl は False/False です（:150）。
- 入力再開は 18:40:46 で、約26分の余裕がありました。

**判断**
- 同じガードの下で左 Ctrl も読んでいれば、同時に解除できた可能性が高いと考えます（※推定）。
- ただし一般論としては、タイマーだけでは足りません（B を参照）。

### 6.【中・確定と推定】調査の時系列で、補正すべき点

| 記述 | 判定 | 根拠 |
|---|---|---|
| IsDown=True／NativeDownSent=True のまま約27分 | 一部言い過ぎ | この状態が続いたのは seq51294 までの約26分です。以後は 0x9（隠し保持）と 0xD（再送信済み）を往復しています |
| 入力再開で通常入力を抑止 | 不足 | 最初の数打鍵（seq51251〜51270）と右 Alt タップは正常に処理されています。抑止されたのは Emacs 対象キーだけです（`:262`） |
| 元のキーは記録されていない | 推定は可能 | 合成されたのは拡張 0x47（Home）と拡張 0x4D（Right）の2件ずつです。直前に ConsumeControl があるので、Ctrl+A（`EmacsBindings.cs:83`）と Ctrl+F（`:80`）の可能性が高いです（※推定） |
| 18:41台の非自前 Ctrl down/up で解除 | 確定 | seq51581〜51589。down は抑止され、up は合成した up に置き換えられています |

### 7.【中・仮説】欠落の原因について

**Ctrl+Alt+Del 仮説と矛盾しない材料**
- 左 Ctrl と左 Alt を押している間に、拡張キー（flags=0x1／0x81）の down/up が約52ms あります（seq51132〜51135）。
- Ctrl と Alt の両方の up が欠けています。
- 両方の async 状態が、そのキーの解放から約3.8秒以内に 0 になっています（seq51134 の asyncRaw=5 から seq51136 の 0）。
- Alt 復旧時の heldMs=4265 から逆算すると、信頼できる up の連続観測が始まったのは、そのキーの解放から約1.8〜2.8秒後です。
- その後、前面プロセスが pid 37420 に変わっています。

**ただし断定はできません**
- 矢印、Home／End、PgUp／PgDn も拡張キーです。
- 例えば、グラフィックドライバの Ctrl+Alt+矢印 や、VM／リモートデスクトップのキーボード解放操作でも、同じ痕跡になり得ます（※推測）。
- `TryReadAlt` が不信頼と判定した理由は記録されていないため、現在のログではこれらを区別できません。

### 8.【低】probe の検証範囲

- `ReconcileReleasedAlt` を reliable=true で直接呼んでいます。そのため、`TryReadAlt` のデスクトップ／整合性レベルの判定は通っていません。
- 再送信の後に監視が働かなくなる点（指摘1）も検証していません。

### 9.【低】その他

- Consume は、Windows 側で既に up になっている Ctrl にも up を送っています（seq51289〜51290）。害はなく、指摘2の修正で発生しなくなります。
- `:375` の `otherControl.IsDown` は古い左 Ctrl も数えます。そのため、右 Ctrl を押すと保留されずにすぐ送信されてしまいます。軽微です。
- `MissedKeyUpTests.cs:35-49` は、現在の故障経路をそのまま期待値にしています。修正後は期待値を逆にする必要があります。

## 観点別の回答

### B. タイマー復旧だけで十分か

- 今回の事例: 十分だった可能性が高いです（指摘5）。
- 一般には不十分です。理由は3つあります。
  1. 1秒の確認期間とサンプル間隔のため、欠落から最短でも1〜2秒は無防備な時間があります。
  2. 前面ウィンドウやデスクトップの関係で読み取りが不信頼な状態が続く間は、解除できません。
  3. 一度再送信されると、二度と検出できません。

最初の入力までに復旧が間に合わない場合に備えて、キー判定と Consume の段階で次の2つが必要です。
- 判定: NativeVisible なのに側別の async が up の Ctrl は、Emacs の修飾キーとして数えない（状態は変えない）。
- Consume: 判定に寄与した側だけを処理する。

Promote は変更不要です。

### C. 除外した古い Ctrl が隠し保持として復活する経路

- 経路はあります。`ConsumePendingControlGesture` だけです（指摘2）。
- 修飾キーの判定だけを変えても不十分です。
- また、隠し保持になった Ctrl は Windows から見えないため、async 状態で検証できません。したがって、その遷移の手前で止めるしかありません。

### D. Alt の復旧方式を Ctrl に流用する際の危険

- **GetAsyncKeyState の値**
  - 0 は物理的な解放を保証しません。
  - フック時点で判定から外す場合、外し方を誤ったときの結果は「Emacs が効かず、Ctrl+キーがそのままアプリに届く」です。Alt の方針（`AltModifierSnapshot.cs:10`）と同じで、安全側の失敗です。
  - タイマー解除を誤った場合（実際は押し続けているのに解除した場合）は、以後のリピートが新規 Start として保留・抑止され、up のときに Ctrl のタップが合成されます（`:402-406`）。害は小さいですが、テストで確認しておくべきです。
- **フック入口の値**
  - フックに入った時点では、処理中のイベントは async 状態に反映されていません。
  - 直前のイベントの反映は観測上は確認できます（seq51131 から 51132 で 1 が 5 に、SendEnd の時点で反映済み）。ただし保証はありません（※未検証）。
  - このため、フック内では判定から外すだけにして、状態を変えるのはタイマーに限るべきです。
- **非自前の新規 down とリピート**: 側ごとの監視を、非自前の down が来るたびにリセットします（Alt の `:439` と同じ）。リピートが続く長押しは解除しません。
- **左右**
  - 判定には VK_LCONTROL／VK_RCONTROL を使います。
  - `AsyncAnyDown`（VK_CONTROL）で古い側を生かしてはいけません。
  - Sides（`ControlModifierSnapshot.cs:12-14`）にも同じマスクをかけます。
- **AltGr**
  - AltGr を持つ配列では、Windows が擬似的な左 Ctrl を生成し、それが `HandleControlEvent` に入ります（※推測）。
  - 擬似 Ctrl の async が down だと、古い左 Ctrl の解除が遅れるだけで、方向としては安全です。
  - 擬似 Ctrl 自体が残った場合の挙動は未検証です。
- **SendInput 中の再入**
  - 既存の深さガード（`:1071`）と監視リセットを流用します。
  - SendNavigation 中に Ctrl を一時的に up にする処理（`:739-742`）も、このガードの範囲内に入ります。
- **前面の変更、デスクトップ／UIPI**: `TryReadAlt` の判定を流用し、L/R Alt と L/R Ctrl の4つを同じ1回の確認で読むよう一般化します。
- **復旧後の遅延 up**: `ControlUnknownUp` として通過します（`:383-386`）。Windows にとっては up の重複なので無害です。回数の記録を推奨します。

### E. 負荷を最小にする観測タイミング

- **フック経路では、追加のシステムコールは不要です。**
  - `GetControlModifierSnapshot` は、Emacs 対象キーの down の時だけ3つの VK を既に読んでいます（`:262`、`:719-721`）。
  - 状態側の NativeVisible フラグを足すだけで済み、Consume にはその snapshot を渡します。
  - リピート処理の修正にもシステムコールは要りません。
- **タイマー（既存の1Hz）**
  - 読み取りを行う条件を「Alt が押下中」から「Alt が押下中、または Ctrl が押下中かつ NativeVisible」に広げます。
  - 隠し保持の Ctrl は検証できないので対象外にします。これで、正当な長い隠し保持の間に重い確認を回さずに済みます。
  - 事前の絞り込みとして、まず側別に GetAsyncKeyState を読み、down なら監視をリセットして重い確認を省けます。不信頼な読み取りは 0 を返すので、1 は「解放されていない」根拠として使えます。
  - 重い確認（`WindowsIdentity.GetCurrent`、`OpenProcess`、トークン照会）は、生の値が up の時だけ実行します。
- 毎キーの権限確認や、全キーの常時走査は行いません。

### F. 原因の特定と影響の抑止を分けた、追加ログの提案

影響の抑止は、上記の修正で原因に依存せず実現できます。原因の特定には、現在のログに次の情報が足りません。

| 不足している情報 | 記録場所 | 条件 | 記録内容 |
|---|---|---|---|
| 不信頼と判定した理由 | `ReconcileReleased*` | NativeVisible の修飾キーが押下中で、判定が変化した時だけ | 理由コード（foreground=0／入力デスクトップでない／トークン失敗／対象の整合性レベルが高い／読み取り中の前面変更）、前面 pid、生の L/R Ctrl/Alt ビット |
| async と内部状態の食い違いが始まった時刻 | 同上 | エピソードごとに1回 | 側、QPC。復旧時には継続時間 |
| Ctrl/Alt 押下中に押された非文字キーの識別 | Trace の Classify | Ctrl か Alt が IsDown の間の down で、許可リスト（Delete、Insert、Home、End、PgUp、PgDn、矢印、Esc、Tab、F キー）に含まれる時だけ | VK。文字キーではないので、プライバシー上の問題はありません |
| セッション切替 | `OnSessionSwitch`（`:972`） | すべての理由 | 理由を1行で |
| Ctrl の復旧 | 新しい復旧処理 | 復旧時 | Alt の `:1096` と同じ形式 |

あわせて、18:14:32 に何を操作したかを利用者に確認してください（Ctrl+Alt+Del、タスクマネージャー、VM など）。

## 対策案の分類

| 案 | 分類 | 理由 |
|---|---|---|
| 1. 通過・送信済みの Ctrl を、継続確認の後にタイマーで解除する | 採用可能 | 既存の Alt のガードと監視をそのまま流用できます。ただし再送信の前にしか効かないため、主対策ではなく補助と明記すべきです |
| 2. Windows 側で解放済みの Ctrl を、判定や再送信に使わない | 修正が必要 | 判定の変更だけでは C の経路が残ります。「再送信に使わない」は、Promote ではなく Consume の側で担保すべきです。押し直しの通過（指摘3）も含める必要があります |
| 3. 意図的な隠し保持は対象外にし、時間切れでは解除しない | 採用可能 | 妥当です。「Emacs で消費された後の隠し保持」も検証できないので対象外になる、と明記してください。取得不能の判定はタイマー経路にしかなく、フック経路は判定から外すだけ、という分担も明記が必要です |
| 4. 既存の1秒タイマーを使い、対象がある時だけ確認する | 採用可能 | E の絞り込みを加えれば、通常時の負荷は増えません |

保留を推奨するもの（追加案）:
- Consume の時点で状態を即座に Reset する方式。フック内の値の信頼性が保証されていないためです。
- フックの再登録や ResetActiveStates に復旧を任せる方式。

## 推奨する処理順序と最小変更範囲

1. **フック経路**
   - `ControlModifierSnapshot.cs`: 側ごとに NativeVisible を持たせ、AnyDown／Sides の計算を Alt の Active と同じ考え方に揃えます。
   - `AltInputService.cs`: `GetControlModifierSnapshot`、`ConsumePendingControlGesture(s)`（寄与した側だけ、古い側は変更しない）。
2. **押し直しの通過**: `HandleControlEventCore` の down 分岐（`:358-362`）。
3. **タイマー復旧**
   - `AsyncKeyStateAccess.cs`: Ctrl も読めるよう一般化します。
   - `AltInputService.cs`: `ReconcileReleased*` を Ctrl に広げ、`DeferredControlState` に監視を追加します。`AltReleaseMonitor` はそのまま流用します。
4. **診断ログ**（F）: 別の変更として切り出します。

## 必須の回帰テスト

1. probe の手順をテスト化します（古い左 Ctrl が残った状態で、F が素の F として通過し、X で Ctrl が再送信されず、模擬 OS 上もすべて up）。
2. 右 Ctrl の実押下＋古い左 Ctrl: 右 Ctrl+F で Right を送り、左は隠し保持にならず、その後 X で左 Ctrl を再送信しない。
3. 管理外の VK_CONTROL（外部注入）＋古い左 Ctrl: 2 と同じ結果になる。
4. 正当な保留 Ctrl を120秒保持してから F を押すと Emacs が働き、続く S で再送信されて Ctrl+S になる（既存の挙動を維持）。
5. 昇格済みの Ctrl（Windows 側も down）: F で Emacs、S で再送信。
6. OriginalDownPassed の Ctrl を長押し: ネイティブの組み合わせはそのまま、120秒でも解除されない。
7. タイマー: 信頼できる up を1秒観測すると解除される。不信頼、前面変更、2.5秒以上の間隔、送信中（深さ）、非自前 down では、確認がリセットされるか、やり直しになる。隠し保持と消費後の状態は解除されない。
8. 古い Ctrl が残った状態での押し直し: down と up が通過し、合成入力はなく、最後は up になる。
9. 復旧後に遅れて届いた up: 通過し、残存も送信もない。
10. 左右の Ctrl のうち片方だけが古い場合。
11. 古い Ctrl が残っている間の Alt タップが、IME のタップとして扱われる。
12. 既存の ModifierReleaseTests、AltRecoveryTests、EmacsTests を全件通す。MissedKeyUpTests は期待値を逆にする。
13. 可能なら、AltGr の擬似 Ctrl の特性テスト。

## 残る不確実性

- up が欠落した原因は未特定です（仮説の段階）。
- フック内の async 値が直前のイベントを反映している、という点は観測にもとづくもので、保証はありません。
- UIPI やデスクトップ切替の状況で、フック内の GetAsyncKeyState がどう振る舞うかは未確認です。
- AltGr の挙動は未検証です。
- 再送信中に実際の Ctrl+キーがアプリにどんな影響を与えたかは、利用者への確認が必要です。
- 本レビューではビルド、テスト、probe を実行していません（未確認）。
