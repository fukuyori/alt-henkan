# Ctrl残留対策 実装レビュー

**結論：** 今回の変更で入った不具合のうち、根拠があり修正必須といえるものは見つかりませんでした。元の欠陥の経路（送信済みCtrlのup欠落 → 誤変換 → hidden化 → 再送信）は、コード上で閉じていることを確認しました。ただし、Ctrlが**hiddenの間にupが欠落した場合**の再送信経路は、既存のまま残っています。これが最大のリスクです。

## 1. 今回の変更で閉じたと確認した経路

- **修飾判定:** 送信済み・通過済み（NativeVisible）で、側別asyncがupの側は除外されます（`ControlModifierSnapshot.cs:16-18`）。総合VK_CONTROLだけでは側が立たないので、左右制限で外れます（`EmacsSideFilter.cs:16-21`）。
- **hidden化:** Consumeは、同じsnapshotで有効だった側だけに限定されています（`AltInputService.cs:264,278,685-691`）。除外された古い側はConsumeされないため、hiddenに戻りません。
- **再送信:** Promoteは hidden の側にしか送信しないため（`:599`）、古い側が再送信されることはありません。キー経路（`:290`）、マウス経路（`:578`）とも同じです。
- **押し直し:** 遅延up・押し直しで入力が合成されないことを確認しました（`:363-369`, `:391-394`）。
- **長押し:** 正常なhidden長押しは監視対象外です（`:1117` で visible が条件）。可視の長押しは、asyncがdownなら監視がリセットされます。
- **タイマー:** 監視はキー処理とは別のフック処理スレッドで動きます。送信中（`_inputInjectionDepth != 0`）はAlt・Ctrlとも監視をリセットします（`:1084-1094`）。
- **負荷:** 無保持時は短絡評価のため状態の問い合わせは0回です（`:1117`）。重い権限照会はvisibleかつ生の値がupのときだけで、AltとCtrlで1回を共有します（`:1106-1107`）。
- **Altの退行:** 旧実装のObserveでリセットされていた条件（hidden・async down）は、事前判定で同じようにリセットされます。重い照会がhidden保持中・押下中に省かれるようになった点だけが差分で、退行は見当たりません。

## 2. 指摘事項

### [高・既存（今回の範囲外）] hiddenのCtrlでupが欠落すると再送信・固着する経路が残る
- 根拠：`AltInputService.cs:290,597-609,1115-1120`、`ControlModifierSnapshot.cs:17-18`
- イベント列（コードで確認済み。実際にhidden中に欠落が起きるかは未確認）：
  1. Emacsモードで LCtrl down → 保留されてhidden（`:388`）
  2. （任意）F → Emacs操作 → ConsumedByEmacs
  3. LCtrl up が観測されない
  4. 次の X → `:290` のPromoteで LCtrl down を送信 → Windows上では Ctrl+X になる
  5. 以後は visible かつ async down なので、タイマーでは復旧しない（`:1117`）
  6. ユーザーが次にCtrlを押して離すまで（`:363-369` → `:397-400`）、Windows側のCtrlが押下のまま残る
- Emacsモード中は、Ctrlを押した直後の通常状態が hidden です。今回の対策は visible 状態での欠落（インシデントではAltによるPromote後）だけを対象にしています。検証文書にもこの限界は書かれていますが、残るリスクとしては最も大きいものです。

### [中・テストの妥当性] `ForeignAltGrSequence` の主要な確認が、修正の有無に関係なく成立する
- 根拠：`ControlRecoveryTests.cs:55-74`、`AltInputService.cs:212`、`EmacsBindings.cs:78-97`
- 理由（コードで確認済み）：
  - `flags: 0x10`（LLKHF_INJECTED）は、本体の振り分けで一切参照されていません。本体が見ているのは ExtraInfo のマーカーだけです。
  - そのため、このテストのCtrlは管理外の入力ではありません。通常どおり保留され、RMenu down でPromoteされる管理対象の経路を通っています。
  - Ctrl+Alt+F に対応するバインドは存在しません（Resolve は完全一致）。したがって `:63` の確認は、今回の修正がなくても成立します。
- 実際に「管理外のCtrl」を確認しているのは `ExcludeStaleSide` の `external=true`（SetDown）だけです。テスト名・確認文と、検証文書の「AltGr相当」という表現は修正が必要です。

### [低〜中・今回の変更による・推測] 正当なvisible Ctrlが、Windows側の状態に反映される前に除外される可能性
- 根拠：`AltInputService.cs:383-387,604-606`、`ControlModifierSnapshot.cs:17-18`
- イベント列（推測）：
  1. LCtrl down（hidden）
  2. RCtrl down → そのコールバックの中で左右とも SendInput で down を送信
  3. すぐに F が来る
  4. 注入したdownがまだasync状態に反映されていなければ、左右とも除外されて素のFが通る
- 旧実装では内部状態だけで Ctrl+F として変換されていました。フック内でSendInputした注入イベントと、すでにキューにあるハードウェア入力の処理順は確認していません。テスト用の模擬環境は同期的に処理するため、このテストでは検出できません。
- Promote の送信が失敗しても NativeDownSent=true になる点は、コードで確認済みです（`:605-606`）。この場合も同じく素通りしますが、Ctrlのリピート（`:363-369`）で自然に回復します。
- Altは既存の `AltModifierSnapshot.Active` で同じ考え方を採っています。設計としては一貫しています。

### [低・今回の変更で範囲が拡大・推測] Consume中のSendInput再入で、内部状態とWindowsがずれる
- 根拠：`AltInputService.cs:700-709,752-755,410-416`
- イベント列（推測）：
  1. visibleのCtrl（NativeDownSent）で F → Consume が Ctrl up を送信
  2. その送信の途中に、同じ側の物理downが再入して届く
  3. 新しい経路 `:363-369` がそのdownを通過させる（旧実装では抑止していた）
  4. Consume に戻ると、フラグが hidden に上書きされる
  5. Windows側は down のままなので、SendNavigation が Ctrl を外さず（`:752`）、Ctrl+Right になる
  6. 物理upは「保留中・消費済み」として抑止される → Windows側のCtrlが押下のまま残る
- OriginalDownPassed の場合は旧実装でも通過していたので既存の問題です。NativeDownSent の場合が今回新たに加わりました。物理入力がSendInput中に再入するかどうかは未確認です（`keyboardCallbacksDuringInjection` の内訳では区別できません）。
- 対策案：フラグをSendInputより前に更新する。またはSendInputの後でdownの版数を再確認する。

### [低・既存] Consumeが EmacsControlSide に関係なく有効な側すべてを消費する
- 根拠：`:689-690` と `:724` の比較
- 設定上Emacsの対象外の側でも、物理的に押下中ならhiddenにされ、後で再Promoteされます。押下中なら結果は整合しますが、その側でupが欠落すると上記「高」の経路に入ります。

### [低・診断・任意改善]
- `heldMs` は最初の Start から計算されます。押し直し（`:363-369`）では DownAtMilliseconds を更新しないため、押し直し後の復旧では実際より長い値になります（`:1129`, `:1297`）。Altも同じ挙動（既存）です。
- 押下時に古い側を除外したこと自体は記録されません。現場で「誤変換の防止が働いた」ことを示せるのは、1〜2秒後の RecoveredControl だけです。除外回数のカウンタを追加すると切り分けに役立ちます。
- `ControlRepeatNative` では、古い状態を引き取ったケースと、正当なPromote後のリピートを区別できません。
- `altReconcileInjectionSkipsWithAlt` には Ctrl の保持が含まれません（READMEに記載済み）。

## 3. 0x19 の制約の扱い

- 確認済み：Ctrl復旧（`:1006`）は再登録の判定（`:1025-1038`）より前に実行されます。0x19 が押下中でもCtrl復旧は妨げられません。
- 影響：復旧後の `RequestRefresh` は、0x19 の high bit が立っている間ずっと保留されます。害はありませんが、実機での自動再登録はまだ確認できていません。
- 名前だけを根拠に除外しないという判断は妥当です。KeyHoldPolicy を変更しないのも適切です。
- 追加で確認したい点（未確認）：0x19 がフックの記録上「押下中」として残っているかどうか。残っていると、Alt単押しがネイティブAlt扱いになり（`:638-643`）、Ctrlの保留もできなくなります（`:648-651`）。状態ログの `otherKeysCount` が0以外の行は複数ありましたが、どのキーかは分かりません。

## 4. 修正必須と任意改善・実機検証の区分

**修正必須（今回の変更による不具合）：** 根拠のあるものはありません。

**修正推奨：**
1. `ForeignAltGrSequence` の名前・確認内容と、検証文書の記述の訂正（中）
2. Consume でフラグを先に更新する（低）

**既存の残存リスク（別対策が必要）：** hidden中のup欠落による再送信・固着（高）

**任意改善：** 除外回数のカウンタ、押し直し時の heldMs、`ControlRepeatNative` の内訳

**実機検証が必要：**
- 注入直後の高速入力で visible Ctrl が除外されないか
- SendInput 中に物理入力が再入するか
- 実際のAltGr配列でスキャンコードがどう扱われるか
- デスクトップ切替・UIPI 環境でのタイマー復旧
- 0x19 の状態がない環境での自動再登録
