# Alt Henkan 0.4.2 入力異常の原因調査レビュー

レモン、レビュー結果です。このリポジトリ内の Read/Grep/Glob だけで調べました。ファイルの変更、ビルド、入力の送信、プロセス操作はしていません。tmp 内の `claude-investigation-review*` と `alt-sequences.json` は根拠に使っていません。

## A. 事実整理の検証(重要度順)

**A1. 原因の中心を「up でも昇格すること」に置くのは飛躍です**
- up で昇格するのは事実です(`AltInputService.cs:306-317`)。
- ただ、3件とも昇格しなかった場合でも、次の Other down で同じ AltSend が起きていました。
  - 今回: seq914 が 905 の約1ms後
  - 09:31: seq998 が 989 の約1ms後
  - 10/23: seq5748 が 5739 の約0.8秒後
- 異常の本体は「物理 Alt の up が Alt up としてフックに届いていない」ことです。up での昇格は、その欠落を Windows 側の Alt 押しっぱなしに変える経路にすぎません。

**A2. 報告の数値は生ログと一致しています**
- 時刻: seq903 は 01:58:55.394Z、seq905 は 56.196、seq1051 は 59:26.253。qpc とアンカーから計算して一致しました。
- 状態: state と asyncRaw の値、sent=1、seq903以降に own=False の右Alt up がないこと、すべて確認しました。
- 補足: own=False の右Alt **down(オートリピート)も1件もありません**。B4 で使います。
- seq1～1508 の連番: 私が通読したのは 903～1069 だけで、この範囲は連続していました。それ以外は未確認です。Trace gap / outage の行は全世代で0件でした。

**A3. 「12件すべて正常とは未確認」の部分は確認できました**
- AltSend down は全世代で15件あります。
- うち12件は直後に AltSentUp(物理 Alt up を受けて up を送信)で閉じています。12件とも左Alt(flags=0x8)です。
- 右Alt の昇格(flags=0x9)は全ログで2件だけで、2件とも異常例です。
- つまり、**右Alt が正常に昇格した比較対象はログにありません**。
- 12件の発生源が Other down であることは、`.input.4:404` の1件だけ照合しました。残りは未照合です。

**A4. ユーザーの操作は完了していません**
- seq903 以降、ImeTap は送信されていません。右Alt による IME 切替は起きていないことがログから確定します。

**A5. EmEditor と言えるのは10:58の1件だけです**
- 今回の PID 24020 は 10:54:40 から稼働し続けているため、10:58 時点の EmEditor と結び付けられます。
- 09:31 の pid=19428 と 10/23 の pid=19228 は未確認です。「同じアプリで3件」とは言えません。

**A6. 抽出基準の見落としの検証**
- 基準は「AltSend/down がある」ことを前提にしているので、Alt が保留のまま up が消えた例は原理的に拾えません。
  - その場合、次の Alt down は AltRepeatHidden になるはずです(`AltInputService.cs:418`)。全世代で0件なので、該当はありません。
  - ただし、Disabled、Reset、Shutdown で閉じた例は残り得ます。
- 別の方法でも同じ3件が出ました。B1 の「対応する down のない Other up」の検索です。
- 残るリスク: 他のキーを押している最中(nonAltKeys≥1)の orphan up は、この検索では拾えません。

## B. 既存ログで確認できたのに使われていなかった証拠

**B1. 対応する down のない Other up は全世代で3件だけで、3件とも今回の事例です【最重要】**
- 検索条件: Enabled、captured=0、KeyBegin 時点で nonAltKeys=0、own=False の Other up。
- 該当: `.input:10970`(seq905)、`.input.1:10806`(seq989)、`.input.3:15210`(seq5739)。
- 3件とも保留中の Alt がある状態でした(state=0x341000 / 0x340100)。それ以外の場面では一度も出ていません。
- 10:58 のセッションでは、通常ログ `AltHenkan-diagnostics.log:1681` が imeWidthEvents=0 を示しており、ImeWidth 経路(`:228-234`)で down が除外された可能性はありません。古い2件は未確認です。
- 判定材料は `_nonAltKeysDown` の件数だけです。この down が実際に失われたのか、記録の対象外になっただけなのかは、通常キーを匿名化しているため区別できません(`InputTrace.cs:20-21`)。
- 確実に言えるのは、**このフックが down を見ていないキーの up**だということです。

**B2. orphan up だけ、フックへの到着が遅れています**
- qpc(ms) − eventTime の差は、通常の打鍵や自前の注入では約23～37msです。
- orphan up だけが大きくなっています。

| 事例 | qpc(ms) − eventTime | 通常との差 |
|---|---|---|
| 10:58 seq905 | 98ms | 約63ms 遅い |
| 09:31 seq989 | 127ms | 約93ms 遅い |
| 10/23 seq5739 | 62ms | 約28ms 遅い |

- 10/23 は GetTickCount の分解能(約15.6ms)の2刻み程度なので、遅延と言えるかは曖昧です。
- 遅延の原因は未判定です。

**B3. 右Alt の2件では、注入直後に人の打鍵とは考えにくい down/up の組が来ています**
- 10:58: seq914 と 916 の eventTime はどちらも 315078 で、注入 seq909 と同じです。到着は注入の 0.9ms 後と 1.5ms 後です。
- 09:31: seq998 と 1000 も、注入 seq993 と同じ 540656 で、0.9ms 後と 1.9ms 後に到着しています。
- down から up まで1刻み(16ms)未満です。通常の打鍵は 60～100ms 程度です。
- どちらも injected フラグ 0x10 はありません。
- 左Alt の 10/23 にはこの組がありません。
- 注入への反応なのか、滞留していた入力がまとめて届いたのかは未判定です。

**B4. 長押しだったとするとキーリピートが出るはずですが、出ていません**
- この環境のリピート遅延と間隔は、`.input.1:5364→5375` から実測できます。
  - LeftControl を押して(eventTime 113734)、最初のリピートが 114250 です。遅延は約516ms、間隔は約31msです。
  - 修飾キーのリピートがフックに届くことも、これで確認できます。
- 一方、3件とも Alt down から orphan up まで 687～766ms あるのに、Alt のリピートが1件もありません。
- 全世代でも AltRepeatHidden は0件です。
- したがって「Alt を押し続けていた」とは考えにくく、次のいずれかと推測されます。
  - 約0.5秒以内に物理的に離したが、Alt up が届かなかった、または別のイベントになった
  - 届いていない別のキーの down がリピートを止めた
- ※推測です。516ms の値は別のセッション・別の時刻の測定で、同じキーボードかどうかは未確認です。

**B5. orphan up のフラグは 0x80 で、拡張ビットがありません**
- 正常な右Alt up は 0x81 です(seq15、09:31 の seq1024)。
- orphan up が右Alt の解放だとしても、E0 付きのスキャンコードとしては届いていません。

**B6. 症状と注入状態のつながり**
- seq914～1033 の Other はすべて flags=0x20(LLKHF_ALTDOWN)です。リセット後の seq1067 では 0x0 に戻っています。
- Windows 側でも Alt を押した扱いだったことは確定です。
- foreground ハンドルが EmEditor 内で 0x30D84 / 0x40D84 に変わっています(seq1009、1033)。Alt+文字でメニューやダイアログが開いた可能性があります。※推測です。

**B7. 復旧の仕組みが働かなかった理由**
- 通常ログ `:1681` と `:1682` は rightAlt=True/False/True、asyncAlt=False/True、sinceRefreshMs=33812 を示しています。
- 自動復旧 AltReleaseMonitor は AsyncDown が true なので対象外です(`AltModifierSnapshot.cs:24`)。
- フックの更新処理も、ジェスチャー中と判定されて抑止されています(`AltInputService.cs:979-984`)。

**B8. 古い2件はユーザーが Alt を押し直して直っています**
- 押し直しで AltRepeatNative から AltPassedUp に進み、復旧しています(`:407-416`。`.input.3:15224`、`.input.1:10840`)。
- ユーザーが気付かなかった理由として考えられます。※推測です。

## C. 3件から言えること・言えないこと

**言えること**
- 3件は同じ流れをたどっています。
  1. Alt を保留する
  2. Alt のリピートがないまま、約0.7秒後に拡張ビットのない orphan Other up が来る
  3. その up で昇格する
  4. 物理 Alt up が届かない
  5. 以後のキーに ALTDOWN が付き、Alt の押し直しかリセットまで続く
- orphan up は、この3件以外では一度も出ていません。
- 頻度: 右Alt は正常タップ179件に対して2件、左Alt は121件に対して1件です。

**言えないこと**
- orphan up がどのキーか(VK とスキャンコードは記録していません)
- 物理 Alt up が失われたのか、別のイベントに変わって届いたのか
- 外部のフック、ドライバ、IME、キーボード本体のどれが関係しているか
- EmEditor に依存するか
- 前2件でユーザーが異常に気付いたか
- フックが新しいものほど先に呼ばれるという順序は、資料で確認していません

## D. 修正前に最優先で行う調査・再現試験

1. **Alt Henkan を無効にした状態で再現を試す(コード変更なしでできます)**
   - 無効でも TraceKeyboard は全キーを記録し、右Alt は分類されます(`InputTrace.cs:91`、経路は `AltInputService.cs:283-286` の Inactive)。
   - EmEditor で右Alt を何十回かタップし、own=False の RightAlt down の後に RightAlt up が必ず来るかを数えます。
   - 無効でも up が欠ける → 外部要因やデバイス側です。
   - 有効で抑止しているときだけ欠ける → 抑止との相互作用です。
   - メモ帳など EmEditor 以外でも同じ比較をします。
2. **ユーザーに確認する事項**
   - キーボードの機種と接続方式(USB か Bluetooth か)
   - 常駐しているキー割り当てソフトやキーボード用ユーティリティ
   - Windows のキーボード「表示までの待ち時間」の設定
3. **修正方針を検討するときの前提**
   - up で昇格しないようにするだけでは、3件とも直後の down で再発します(A1)。
   - 正当な Alt 長押しとの区別について:
     - 現行の設計では、Alt より前に押したキーがあると Alt は保留されず、そのまま通ります(`:431-442`)。そのため、保留中の orphan up は正当な操作の一部にならないはずです。
     - 正当な長押しなら、約516ms 以降に AltRepeatHidden が約31ms 間隔で出ます。
   - ただし、リピートは他のキーを押すと止まり、遅延もユーザー設定で変わります。リピートの有無だけで解放と判定するのは危険です。
   - 判定材料として使えるのは「orphan up」と「Alt リピートの欠如」の組み合わせです。それでも、orphan up の正体が分かるまでは方針を決めない方がよいです。

## E. 追加観測が必要な場合(無差別な文字収集はしない)

| 未判定の問い | 最小限の観測 | 区別できること |

| Q1 orphan up はどのキーか | 保留中の Alt があり、かつ追跡外のキーの up が来たときの1件だけ、VK・スキャンコード・フラグを記録 | 0x38 系なら Alt の解放が別コードで届いた/IME 系 VK ならレイアウトや IME、デバイス由来/通常の文字ならそのキーの down が失われた |

## 今確定できる結論
- 右Alt の down を保留した後、0.8秒後に**このフックが down を見ていない Other up** が来ました。それで昇格して右Alt down を注入し、無効化するまで約30秒、Windows 側で Alt が押されたままになりました。この間、後続のキーには ALTDOWN が付いていました。
- その間、物理的な右Alt の up もリピートも、フックに一度も届いていません。
- 同じ流れは全世代で3件あり、orphan up はこの3件以外では一度も起きていません。
- orphan up の正体と、Alt up が失われた場所は未判定です。up での昇格は原因ではなく、症状に至る経路の一部です。
