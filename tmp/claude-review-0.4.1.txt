レビューの結論として、マージを止めるほどの重大な欠陥は見つかりませんでした。報告された「内部では Alt が押下中、Windows 側は解放済み」という食い違いには、筋の通った対策になっています。特に効いているのは、Emacs の Alt 判定を実際の押下状態に切り替えた点です。古い Alt 状態のせいで通常の文字が Alt ショートカットに変わる現象は、1秒の待ち時間を待たずにすぐ止まります。ただし、中程度の問題が1件、効いていないコードが1件、テストが実際の経路を通らない点があります。

## 指摘（重大度順）

### 1. 【中】古い Alt 状態が残っている間に Alt を押し直すと、押したまま内部状態が解除される（今回の変更と既存の処理が組み合わさって起きる）
- **場所**: `src/AltHenkan/AltInputService.cs:382-386`（既存）と `AltInputService.cs:978-987` / `AltInputService.cs:1067-1069`（今回）
- **発生条件**: 送信済み（`NativeDownSent=true`）の Alt 状態が残ったまま、ユーザーが同じ側の Alt を押し直す。
- **何が起きるか**:
  - 既存の処理は `state.IsDown` を見て、この押下をキーリピートとみなして抑止します。そのため Windows 側は解放のまま、ユーザーは実際には Alt を押している状態になります。
  - `Start()` が呼ばれないので監視もやり直されません。前からの計測が続き、1秒たつと押したままの Alt が解除されます。
  - 解除後、次のリピートが来るまでの間に押したキーは Alt なしで届きます。その後のリピートで新しい操作として始まるため、`DownAtMilliseconds` が実際より遅くなります。
  - 結果として、長押しのつもりが短押しと判定され、IME 切り替えが送られることがあります。
  - 復旧するまでの最初の Alt タップが消える問題は既存のものですが、残ったままです。
- **修正方針**: 押下を受けたとき、`state.IsDown && (OriginalDownPassed || NativeDownSent)` なのにその側の Windows 状態が解放なら、古い状態と判断して `Reset()` し、新しい操作として `Start()` からやり直してください。
  - 前のイベントの非同期状態はフック内でも反映済みなので、この判定はフック内で使えます。
  - 少なくとも、物理 Alt の押下を受けた時点で `ReleaseMonitor.Reset()` を呼ぶべきです。

### 2. 【中・既存】抑止中の Alt の解放通知が欠けると、同じ種類の全体的な入力異常が無期限に続く（今回は対象外）
- **場所**: `AltModifierSnapshot.cs:10`（`TrackedDown && !NativeVisible` なら有効と判定）と `AltInputService.cs:910-915`
- **発生条件**: 長押し判定中や Emacs 操作で使った Alt（Windows に見せていない Alt）の解放イベントを、フックが受け取れなかった場合。
- **影響**:
  - Emacs モードでは、Alt ショートカットに割り当てた通常の文字（F、B など）が常にナビゲーションに変わります。
  - `gestureActive` のままになるので、フック再登録も永久に行われません。
  - 今回の復旧は Windows に見せた Alt だけを扱うため、このケースには効きません。文書に未対応と書いてあるのは妥当です。
- **補足（仮説）**: フックが `LowLevelHooksTimeout` を超えると、Windows は抑止するはずだった Alt の押下をそのまま通します。その後に解放を抑止すると、今度は Windows 側で Alt が押しっぱなしになります（`AltInputService.cs:438-474` はすべて `SuppressKeyboardEvent`）。
- **修正方針**:
  - 抑止中の Alt の解放時に、その側の Windows 状態が押下なら、解放を抑止せずそのまま通してください。安価な対策です。
  - 抑止中の Alt の解放欠落については、別途対策が必要です。無入力時間などを使ったタイムアウトは正常な長押しを壊すおそれがあるので、慎重に検討してください。

### 3. 【低〜中】`_inputInjectionDepth` による除外は実際には一度も働かない
- **場所**: `AltInputService.cs:735-757`、`AltInputService.cs:965`
- **根拠**:
  - 保守タイマーはフック処理スレッド上の `System.Windows.Forms.Timer` です（`AltInputService.cs:63`）。
  - `SendKeyboardInputs` は同じスレッドで同期的に実行され、途中でメッセージを処理しません。`InputInjectionFailed` の処理も `BeginInvoke` で返るだけです（`TrayApplicationContext.cs:174`）。
  - したがって `ReconcileReleasedAlts` の時点で深さは常に 0 です。
- **影響**:
  - 今のところ害はありません。Emacs 操作の「Alt 解放 → ナビゲーション → Alt 復元」は1回の `SendInput` で送られ、一瞬の解放は1秒の連続確認で吸収されるからです。
  - ただし README と CHANGELOG の「キー送信中は確認をやり直す」という記述の裏付けは、実際にはこの除外ではありません。
  - `AltRecoveryTests.cs:45-49` は起こりえない状態を人工的に作って合格しているので、安心材料になりません。
- **修正方針**: 次のどちらかにしてください。
  - 除外を削除し、文書を「1秒の連続確認で吸収する」と直す。
  - 送信時刻を記録し、前回の確認以降に自前で Alt を送っていたら連続確認をやり直す。

### 4. 【低】フック内の非同期状態に頼るようになったことによる回帰の可能性（仮説）
- **場所**: `AltInputService.cs:595`、`AltInputService.cs:640-641`、`AltInputService.cs:673-676`
- 以前は Windows に見せた Alt を `IsDown` だけで有効とみなしていましたが、今は Windows 側の押下状態が必要です。
- 前のイベントの非同期状態は、次のコールバックの時点で反映済みです。そのため通常の Alt+キーでは問題ないと判断しました。
- ただし `SendInput` が失敗して `NativeDownSent` だけ立った場合は、動きが変わります。Alt+F が Emacs 操作にならず、通常の F が通り、1秒後に内部状態が解除されます。
  - Windows が見ている状態とは一致するので、むしろ正しい動きだと考えます。
- 自前で送った Alt 押下と物理キーの順序が入れ替わる、ごくまれな競合の可能性も残ります。こちらは実機で確認していません。

### 5. 【低】`AsyncKeyStateAccess` の細かい点
- **毎秒の問い合わせ**: `AsyncKeyStateAccess.cs:19-20` は、Alt を押している間、毎秒 `WindowsIdentity.GetCurrent()` と自プロセスのトークン情報を取得しています。
  - 自プロセスの整合性レベルと UIAccess はプロセスの実行中に変わらないので、起動時に1回取得して保持すれば十分です。
- **例外**: `catch` が受けるのは `SecurityException` と `UnauthorizedAccessException` だけです。
  - それ以外の例外は `MaintainHooks` の catch に落ち、`_refreshRequested=true` と「Hook renewal failed」のログが毎秒繰り返されます。
- **整合性の比較は安全側の近似です**:
  - 管理者権限のウィンドウが前面にある間は復旧しません。これは意図どおりです。
  - `GetAsyncKeyState` が整合性レベルの差で本当に 0 になるかは確認していません。仮説として、安全側に倒れる方向の誤差にとどまると考えます。

## テストについて

- **`RunNative` は実際の経路を通りません。**
  - `ReconcileReleasedAlt` に作った値（`foreground=1`、`reliable` など）を直接渡しています。
  - `MaintainHooks → ReconcileReleasedAlts → TryReadAlt` の配線は検証されていません（深さ≠0 で早期に戻る分岐だけが通ります）。

- **`Run` は判定ロジック単体のテストです。**
  - `AltModifierSnapshot` / `AltReleaseMonitor` / `NavigationInputPlan` は検証しています。
  - しかし `SendNavigation`、`GetNavigationModifiers`、`GetEmacsSideFilter` が `GetAltSnapshot` を使っていることは検証していません。これらが `IsDown` に戻っても検知できません。

## 問題がないと判断した点
- `AltReleaseMonitor` の連続確認の条件（取得不能、前面ウィンドウの切り替え、2.5秒を超える間隔、押下の観測でやり直す）は正しいです。
- `Start()` と `Reset()` での監視のリセットも正しく入っています。
- 抑止中の Alt と押下中の Windows 側 Alt は、何秒たっても復旧の対象になりません。
- 復旧してもキー入力は送らず、Emacs の選択モードは保持されます。
- 復旧の直後、同じタイマー処理で無入力なら再登録まで進みます。
- 左右の Alt で処理は対称です。
