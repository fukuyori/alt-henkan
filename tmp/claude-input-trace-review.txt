# 診断ログ強化（未コミット差分）のレビュー

レモン、レビュー結果です。対象ファイルはすべて読みました。新規ファイルも全文を読んでいます。ファイルの変更、ビルド、テストの実行はしていません。

**結論:** 確実なバグと断定できるものは見つかりませんでした。最も重いのは、ログ機能とは関係なく実入力に効く「自前入力マーカーの形式変更」です。これはネイティブ環境で一度も検証されていません。そのほかは診断上の欠落と改善提案です。

## 1. 回帰リスク（要実機確認）: 64ビットで自前入力マーカーの形式が常に変わる

- **場所:** `src/AltHenkan/AltInputService.Trace.cs:16-25`、`src/AltHenkan/AltInputService.cs:790`、判定箇所 `AltInputService.cs:209`
- **発生条件:** 64ビットプロセスでアプリが入力を送るたび、つまり全ての `SendInput` 呼び出しで発生します。ログの有効・無効に関係しません。
- **変更内容:** これまでの `ExtraInfo` は `0x414C5448` でした。今回 `0x414C5448_xxxxxxxx`（マーカーを上位32ビット、トークンを下位32ビット）に変わりました。`IsOwnInput` は上位32ビットで判定します。
- **影響:** フックで受け取る `dwExtraInfo` に上位32ビットがそのまま届かない環境があると、自前入力を物理入力と誤認します。その場合、送った Ctrl down を `HandleControlEvent` が再び保留・抑止します。これは入力そのものの異常につながります。上位ビットが届かない環境が実在するかは不明です（※推測です）。
- **根拠:** `--native-hooks` テストは `Enabled = false` のままで、入力も送りません（`tests/AltHenkan.LogicTests/Program.cs:188-191`）。`InputTraceTests` は `FakePlatform.Send` が `ExtraInfo` をそのまま戻すだけです（`InputTraceTests.cs:252`）。そのため、Windows を経由した往復は 1161 件のテストのどれにも含まれていません。
- **修正案:**
  - 配置を逆にします。下位32ビットに従来のマーカーを置き、トークンは上位32ビットに入れます。判定は `(uint)marker == 0x414C5448` にします。これなら上位ビットが失われてもトークンが消えるだけで、自前入力の判定は従来どおり保たれます。
  - 実機では、Ctrl保留からの送信を1回行います。そのうえで `own=True` かつ `token≠0` の `KeyBegin` 行が出ることを確認します。

## 2. 診断上の欠落: 保持期間が短く、ローテーション後に見出し行が残らない

- **場所:** `src/AltHenkan/InputTrace.cs:65-66,110,117-118,146-153`、`src/AltHenkan/RotatingDiagnosticWriter.cs:34-45`
- **発生条件:** 普段どおりに入力を続けた場合です。
- **影響:**
  - 1行には未使用の0値フィールドも含め全フィールドが出ます。さらに `session`（32文字）、`utc`、`frequency` が毎行に付きます。私の見積もりでは1行あたり約450〜500バイトです（※推測です）。
  - 通常キーは1打鍵で down と up の各 `KeyBegin`/`KeyEnd`、計4行になります。この場合 20 MiB は約1万打鍵分です。Ctrl・Emacs 操作ではもっと多くの行が出ます。症状が出たあとに再起動して作業を続けると、発生時の記録は数時間以内に押し出される可能性があります（※推測です）。
  - `version`、`schema`、`qpc` 基準値を含む見出し行は、セッション開始時に1回だけ書かれます。ローテーション後のファイルには残りません。通常ログ側も 1 MiB×5 で別々に回るため、`Session started` 行も消える可能性があります。
- **修正案:**
  - 0値・既定値のフィールドを省きます。または固定順の短い形式にします。
  - `session` と `frequency` は見出しに移します。
  - `RotatingDiagnosticWriter` に「ローテーション直後に見出しを書く」コールバックを追加します。
  - README には、発生後すぐにログを退避する手順を明記します。

## 3. 診断上の欠落: 書き込み失敗が復旧せず、原因も残らない

- **場所:** `src/AltHenkan/InputTrace.cs:58,131-135`、`src/AltHenkan/AltInputService.cs:1095`
- **発生条件:** ローテーション（`Rotate`）中の `File.Move` 失敗、ディスク容量不足など、書き込み中の例外です。
- **影響:**
  - 書き込みスレッドが終わり、そのセッションでは以後一切記録されません。
  - それでも `_writer` が残るため、`Enabled` は true のままです。フック側は状態取得とキュー追加を続け、その結果はすべて `Dropped` に計上されます。負荷だけが残ります。
  - 通常ログに出るのは `traceWriteError=IOException` という型名だけで、原因の文面は残りません。しかも30秒ごとの状態記録にしか出ません。
- **修正案:**
  - 失敗時に通常ログへ例外の全文を1回書き込みます。
  - `Enabled` は書き込み処理が生きているかで判定します。
  - 可能なら、次の周期で開き直しを再試行します。

## 4. 診断上の欠落: Ctrl／Alt をそのまま通した理由を区別できない

- **場所:** `AltInputService.cs:348-351`（`ControlNative`）、`AltInputService.cs:427-438`（`AltNative`）、状態取得 `AltInputService.Trace.cs:27-47`
- **発生条件:** Ctrl の押下が保留されずに通過した場合です。
- **影響:** 理由として次の3つが考えられますが、ログ上は区別できません。Ctrl状態が疑わしい今回の調査では、この判断材料が中心になります。
  - `CanDeferControl` が false（設定、Emacs 無効、左右の指定）
  - `_nonAltKeysDown` に古い記録が残っている
  - Shift／Win が押されていると判定された
- `_nonAltKeysDown.Count` は通常ログの30秒ごとの記録にしか出ず、入力イベントログの状態には入っていません。
- **修正案:**
  - 理由を `ControlNativeNotDeferrable` と `ControlNativeOtherInput` に分けます。
  - 状態に `_nonAltKeysDown.Count` を加えます。件数だけなので匿名性は保たれます。

## 5. 診断上の欠落: 終了時に「戻った」瞬間が記録されない

- **場所:** `AltInputService.cs:1001-1015`、`InputTrace.cs:155-159`
- **影響:**
  - 「アプリ終了で戻る」という症状で最も情報が得られるのは、フック解除の直後です。しかし `ResetActiveStates` のあとに `UnregisterHooks` を行った後の状態（`asyncRaw`）は記録されません。
  - 終了時の書き出しを2秒待つ処理で、`Wait` の戻り値が使われていません。時間切れで記録が失われても痕跡が残りません。
- **修正案:**
  - `UnregisterHooks()` の後に `TraceState(Shutdown, after: true)` を追加します。
  - `Dispose` で時間切れになった場合は、その旨を通常ログに書きます。

## 6. 診断上の欠落: 通常ログと入力イベントログを対応付けにくい

- **場所:** `AltInputService.cs:1069,1072-1095`
- **影響:**
  - 通常ログの時刻は `DateTimeOffset.Now` です。入力イベントログの時刻は開始時のUTCに経過時間を足した換算値です。両者は時計の調整でずれます。
  - `WriteHookStatus` が入力イベントログに出す `Boundary Maintenance` 行は、どの状態記録（定期、設定変更、終了など）だったのかを区別しません。
  - フックへの呼び出し回数も入力イベントログには出ません。フックが外れて呼ばれなくなっても、入力イベントログでは「単に入力がなかった」状態と区別できません。
- **修正案:**
  - 通常ログの状態記録に、入力イベントログの最新 `seq` を加えます。
  - `Boundary` 行に、記録の種類とキーボード・マウスの呼び出し回数を入れます。

## 7. 文書と実装の不一致

- **場所:** `AltInputService.Trace.cs:115-116,153`、`AltInputService.cs:185-190`
- **内容:**
  - README は `nextResult` を「後続フックからの戻り値」と説明しています。しかし `verdict=Suppressed` の行では、アプリ自身が返した `1` が入ります。
  - 例外のあと `KeyboardHookCallback` は次のフックへ入力を渡しますが（`AltInputService.cs:189`）、そのことも戻り値も記録されません。
- **修正案:**
  - README を「抑止時はアプリの戻り値」と直します。または項目名を `result` に変えます。
  - 例外後に次のフックへ渡したことを1行記録します。

## 8. 診断上の欠落: 設定の中身が記録されない

- **場所:** `AltInputService.cs:127-155`、`AltInputService.Trace.cs:37`
- **内容:**
  - 状態に入っているのは `Enabled` と `EmacsEnabled` だけです。
  - 保留の判断に関わる `EmacsControlSide`／`EmacsAltSide`、長押し設定、ショートカット設定は、入力イベントログにも通常ログにも出ません（grep で確認済み）。
  - そのため、設定変更の前後で何が変わったかを追えません。
- **修正案:** 設定変更時に、キー内容を含まない列挙値・真偽値を通常ログに記録します。

## 9. 匿名化の説明に不足（改善提案）

- **場所:** `AltInputService.Trace.cs:95-97`、`AltInputService.cs:792-794`
- **残る情報:**
  - 通常キーでも、打鍵数、押下・解放の時刻、前面プロセスIDは残ります。
  - `flags` の拡張キービットで、矢印キーなどの一部を判別できます。
  - Emacs 操作では `sentScan` が出るため、送った矢印キーなどから、元のショートカット（例: Ctrl+F）が推定できます。
- **影響:** 例えばパスワード入力欄での文字数や打鍵リズムが残ります。
- **修正案:** README の「匿名」の説明に、これらの情報が残ることを明記します。必要なら、通常キーの `flags` から拡張ビットを除きます。

## 10. 負荷（改善提案）

- **場所:** `AltInputService.Trace.cs:57`、`AltInputService.cs:792`
- **内容:**
  - 記録1件ごとに、状態取得で `GetAsyncKeyState` を最大7回呼びます。
  - Ctrl保留から送信までの流れでは、`KeyBegin`、状態2行、`SendBegin`、`SendItem`、`SendEnd`、`KeyEnd` で約7件になり、呼び出しは数十回になります。
  - `SendItem` 行はフラグなど送信内容を記録するだけで、毎回の状態取得は要りません。
  - 実際の負荷は `elapsedTicks` で測れるので、実機ログの分布を確認するのがよいです。
- **修正案:** `SendItem` では状態取得を省きます。

## 11. Alt 状態復旧の直前状態が残らない（改善提案）

- **場所:** `AltInputService.cs:1063`
- **内容:** `RecoveredAlt` は復旧後の状態しか記録しません。復旧前のフラグは通常ログにしか残りません。
- **修正案:** 復旧前にも `TraceState` を記録します。

## テストで確認できている範囲と不足

**確認できていること:**
- 偽の入力層（`FakePlatform`）上で、実際の処理経路の状態遷移が記録されること
- 再入時と例外時に、親の観測ID・送信IDが元に戻ること
- 部分送信・送信0件・例外の区別
- キュー満杯時の欠落記録、生成時の書き込み失敗、ローテーション後のファイル数

**不足していること:**
1. **自前入力マーカーの実機往復（指摘1）が未検証です。** 「送信の開始から完了までの間に自前入力が観測される」というテスト（`InputTraceTests.cs:156-163`）は、偽の入力層が同期的に配送する前提です。Windows 上でこの順序になることは示していません。
2. 書き込み中の失敗（ローテーション失敗など）と、終了時の2秒待ちの時間切れは未テストです。
3. テスト用コンストラクタでは `_hookThread` が null です。そのため `UpdateSettings`、サスペンド、ロックの経路は実行されていません（`AltInputService.cs:168` では何もしない）。
4. 記録の有効・無効で、入力の判定結果と送信内容が同じになるかを比べるテストがありません。
5. 匿名化テストの `!text.Contains("key=X ")` は、列挙型に X がないので必ず成立し、意味のある検証になっていません（`InputTraceTests.cs:145-146`）。
6. これらのテストは観測の仕組みを検証するもので、実機障害の原因を示すものではありません。

## 未検証点

- 64ビットの `dwExtraInfo` 上位32ビットが、フックまでそのまま届くか
- 実機での1打鍵あたりの行数と1日あたりのログ量（20 MiB で何時間分を保持できるか）
- 実機でのフック処理時間（`elapsedTicks`）の分布
- 他のアプリがログファイルを開いているときに、ローテーションが失敗するか
