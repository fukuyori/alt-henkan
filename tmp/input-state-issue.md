## 問題

使用中に、Windows全体の文字入力が正常に行えなくなる現象が非常にまれに発生する。利用者からはBackspaceが `^H` になる症状も報告されているが、Backspace自体を発生原因と判断できる証拠はない。alt-henkanの無効化または終了で入力が戻ったとの報告がある。

原因は未確定。発生頻度が低いため、通常使用時の追加負荷を抑えながら、再現時に原因を区別できる情報を保存する必要がある。

## 現時点の確認事項

- 採取したログには、Altを保留した後、通常キーとして分類された解放通知を契機にAlt押下を合成送信する経路が記録されている。
- 利用者が異常を確認した区間では、その後アプリを無効化するまで、対応する右Alt解放通知がログ上で確認できなかった。無効化時にはAlt解放を合成送信している。
- 通常キーは `Other` に匿名化されており、この通知の具体的なキーは判別できない。内部の保持キー数が0であることも、過去に押下通知を受けていない証明にはならない。
- Windowsから取得したキー状態と、物理キーの状態は区別する必要がある。

## 参考事例

利用者はalt-henkanを使用する以前にも、PowerToys Keyboard Managerで似た症状を経験している。両アプリの同時使用による干渉を示す報告ではない。

- https://github.com/microsoft/PowerToys/issues/46693
- https://github.com/microsoft/PowerToys/pull/46672
- https://github.com/microsoft/PowerToys/issues/31571

PowerToys #46693は、AltGrの内部状態の解除漏れにより後続のCtrl解放処理が正しく行われなくなる不具合。修正は、状態を立てる処理を押下時だけに限定し、右Alt解放時にはショートカット実行中かどうかによらず解除するもの。

alt-henkanには同じ解除条件は見つかっていないため、この修正をそのまま移植して原因が解消するとは判断していない。参考にするのは、連続操作の回帰テストと解放後の内部状態検査。

## 今回の対応

- [x] AltGr相当のCtrl・右Alt操作後にCtrlショートカットを使う回帰テストを追加する。
- [x] 反復操作、追加キーの同時押下、キーを離す順序を検証する。
- [x] 左右Alt・Ctrlの解放処理後に残存状態を検査し、不整合時だけ診断を記録する。
- [x] 処理中に新たな押下が入った場合の誤検知と、同一不整合のログ連発を防ぐ。
- [x] 正常時の検査に追加のポーリング・OS呼び出し・ログ出力を持ち込まず、テストで検証する。
- [x] ドキュメントを更新し、テスト結果と検証範囲を記録する。

## 実装・検証結果（2026-10-24）

ローカル作業ツリーに実装済み。コミット・プッシュ・リリースはこの対応では行っていない。

- `ModifierReleaseTests.cs`：左右Ctrl／Alt、Emacs有効／無効、解放順序、1回／3回の反復、追加キー保持の64組み合わせを検証。
- `AltInputService.ReleaseAudit.cs`：解放処理終了時に残るフラグを通常ログと入力イベントログへ記録。観測番号、対象修飾キー、残留ビット、通知時刻を対応付ける。入力処理や状態の自動修復は変更しない。
- 意図的な送信例外で残留状態を作り、記録内容、重複抑止、正常復帰後の再検出を検証。入力イベントログ停止中も通常ログに記録されることを確認。
- 処理中に新しい押下が入る再入テストで誤検知しないことを確認。このイベント順序が自然発生すると実証したものではない。
- PowerShellで `dotnet run --project tests/AltHenkan.LogicTests/AltHenkan.LogicTests.csproj -c Release` を実行し、**1,480件すべて成功**。`git diff --check` 成功。
- 正常な解放の検査を左右Alt／Ctrlそれぞれ10万回測定し、管理ヒープ割り当て0バイト、追加のキー状態問い合わせ0回。実ハンドラーの検査なし約0.97～1.19 msに対し、検査あり約3.33～3.54 ms。これはローカルの限定的な測定であり、アプリ全体のCPU負荷や実際の入力遅延を保証する値ではない。

自然発生する入力異常の再現・原因特定は未完了のため、このIssueは開いたまま継続する。

入力処理の仕様変更や原因特定済みの修正としては扱わない。内部状態が解除されていても、解放通知の欠落や送信失敗を含むすべての入力異常をこの検査だけで検出できるわけではない。より詳しい再現時ログの設計・原因調査は継続する。
