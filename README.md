# Alt Henkan

ソースのバージョンは **0.4.2** です。変更履歴は [CHANGELOG.md](CHANGELOG.md) を参照してください。

0.4.2では、入力異常に至る経緯を追うための継続的な診断ログを追加しています。保存内容・採取方法・検証範囲は[診断](#診断)を参照してください。入力異常そのものの原因は未確定です。

Alt Henkan は、左右の Alt キーを単独で押したときに追加の役割を与える、Windows の通知領域(システムトレイ)常駐アプリです。

- 左 Alt を単押し: IME をオフにする(`VK_IME_OFF`)
- 右 Alt を単押し: IME をオンにする(`VK_IME_ON`)
- Alt を単独で長押しして離す: その側で有効にしていれば、Windows 本来の Alt 単独操作(メニューバーのフォーカスなど)を実行する
- Alt を押したまま他のキーを押す、またはマウスのボタン・ホイールを使う: 通常の Alt との組み合わせをそのまま通す

長押し動作は左右の Alt で個別に有効・無効を切り替えられます。しきい値の既定値は 600 ミリ秒で、設定画面から変更できます。

IME のオン・オフは仮想キー `VK_IME_ON` / `VK_IME_OFF` として送信します。物理キーボードが US 配列でも動作し、IME 側のキー割り当て設定にも依存しません。これらの仮想キーは Windows 10 バージョン 1903 以降の Microsoft IME で対応しています。

## 動作環境

- Windows 10 または Windows 11
- .NET 8 Desktop Runtime(ソースからビルドして実行する場合。インストーラー版は自己完結型のため不要)

## 管理者権限のウィンドウについて

Windows の UIPI により、通常権限のプロセスは、管理者権限で動作しているウィンドウ宛てのキー入力を見ることも、そこへ入力を注入することもできません。そのため、通常ビルドの Alt Henkan は管理者権限のアプリが前面にある間は何もしません。リリースビルドでは `uiAccess="true"` のマニフェスト(`src/AltHenkan/app.uiaccess.manifest`)を埋め込み、Alt Henkan 自体を管理者権限で動かすことなくこの制限を解除します。Windows がこのマニフェストを有効にするのは、実行ファイルが「マシンで信頼された証明書でコード署名されている」かつ「Program Files 配下にインストールされている」場合に限られます。未署名の uiAccess 実行ファイルや、他のフォルダーから起動したものは起動を拒否されます。

`dotnet build` と `dotnet run` では通常の `app.manifest` が埋め込まれるため、開発ビルドは従来どおり `bin\` から起動できますが、UIPI の制限を受けます。

## インストール

`AltHenkan_Setup_<version>.exe` を実行してください。インストーラーはマシン単位(Program Files 配下にインストール、管理者権限が必要。上記を参照)で、次のオプションがあります。

- サインイン時に自動起動する(`HKCU\...\Run` に値 `AltHenkan` を登録。アンインストール時に削除)
- デスクトップにショートカットを作成する(既定ではオフ)

`-NoUiAccess` で作成したインストーラーはユーザー単位(管理者権限不要、`%LOCALAPPDATA%\Programs` 配下)になり、管理者権限のウィンドウでは動作しません。

## 使い方

メインウィンドウはありません。通知領域のアイコンをダブルクリックするか、右クリックして `設定...` を選ぶと設定を変更できます。

設定は `%LOCALAPPDATA%\AltHenkan\settings.json` に保存されます。

### 統合設定とEmacsモード

設定画面は `Alt設定`・`Emacs設定`・`表示設定` の3タブです。既存のAlt長押し設定と判定時間を引き継ぎます。

`Emacs設定` の「CapsLockによるEmacsモード切り替えを有効にする」をONにすると、CapsLockで通常モード／Emacsモードを切り替えます。機能は初期状態ではOFFです。「初期モード」で通常／Emacsを選択でき、既定値は通常です。この設定はアプリ起動時と、機能をOFFからONへ戻した時に適用します。その後にCapsLockで切り替えた現在のモードは保存しません。機能をOFFにすると通常モードに戻り、CapsLock本来の大文字固定を使えます。機能を有効にした際は、大文字固定がONなら解除します。

Emacsモードでも文字・数字・記号の入力は通常どおりです。次の13種類の移動・削除ショートカットのみ変換し、それぞれを個別にON／OFFできます（各操作の既定値はON）。

| キー | 操作（送信するキー） |
|---|---|
| Ctrl+B / Ctrl+F | 左 / 右 |
| Ctrl+P / Ctrl+N | 上 / 下 |
| Ctrl+A / Ctrl+E | Home / End（行頭 / 行末） |
| Alt+B / Alt+F | Ctrl+左 / Ctrl+右（前 / 次の単語） |
| Alt+< / Alt+> | Ctrl+Home / Ctrl+End（文書の先頭 / 末尾） |
| Ctrl+D | Delete（カーソル位置の文字を削除） |
| Alt+D | Ctrl+Delete（次の単語を削除） |
| Ctrl+K | Shift+End → Delete（行末まで削除。行末では改行を削除して次の行と結合） |

実際の移動・削除範囲は対象アプリの矢印・Home・End・Ctrl+矢印・Deleteなどの動作に従います。ONの操作は対象アプリ本来のショートカットより優先します。たとえばCtrl+Aの全選択、Ctrl+Pの印刷、Ctrl+Fの検索は該当項目をOFFにすると使えます。Ctrl+Vなど上記以外のショートカットは変換しません。viモードは含みません。

US配列のAlt+<はAlt+Shift+`,`、Alt+>はAlt+Shift+`.`です。この2種類はShiftを必要としますが、その他の操作にShiftを追加した組み合わせや、Ctrl+Alt・Windowsキーを追加した組み合わせは変換しません。

`Emacs設定` の「Ctrlの対象」「Altの対象」で、それぞれ「左」「右」「両方」を選べます。モード全体で共通の設定で、既定値は「両方」です。「両方」は左右どちらのキーでも使える意味で、同時押しは不要です。「左」「右」は指定した側が押されているときに変換し、対象外の側だけで押した操作は通常どおり通します。この指定はAlt単独のIMEオン／オフや長押し設定には影響しません。旧バージョンの設定では左右とも「両方」となり、既存の個別ON／OFF設定を引き継ぎます。

削除操作は切り取りではなく、クリップボードへ保存する処理やEmacsのkill ringは実装しません。Ctrl+Kは対象アプリのShift+Endで選択し、Deleteで削除します。折り返し行や既存の選択範囲がある場合の挙動も対象アプリに従うため、Emacsの論理行単位の削除と完全に同一ではありません。

Altを使う上記の操作を実行した後にAltを離しても、IME切り替えを送りません。それ以外のAlt単独操作・組み合わせは従来の動作を保ちます。

`表示設定` では、切り替え時の「通常モード」「Emacsモード」の画面表示をON／OFFできます（既定値はON）。表示は約1.2秒で消え、入力中のウィンドウからフォーカスを移しません。画面表示がOFFでも、通知領域のメニューとアイコンのツールチップで状態を確認できます。トレイの「有効」をOFFにすると、Alt変換とEmacs機能の両方を停止します。

### 長時間稼働時のフック維持

入力フックは設定画面とは別の専用スレッドで処理し、診断ログの書き込みと通知表示はフックから切り離しています。
Windows が通知なくフックを解除した場合に備え、30 秒ごとに再登録を予約し、1 秒以上無入力で、キー・マウスボタンが押されておらず、Alt・Emacs操作の途中でもない時点で再登録します。操作が続いている間は再登録を延期します。Emacsの選択モードは再登録後も維持します。
スリープ復帰・ロック解除・「有効」のオフ→オン時にも再登録を予約します。

Windowsへ押下を通過・送信済みのAltについて、アプリ内では押下中なのにWindows側は解放済みという食い違いが続いた場合は、内部のAlt状態を解除します。1秒周期の確認で、同じ前面ウィンドウに対する解放状態を1秒以上連続して確認してから解除し、無入力時のフック再登録を予約します。この復旧でAltの押下・解放やIME切り替えを新たに送ることはありません。Emacsの選択モードも保持します。

Altの追加押下を受けた時点で復旧監視をリセットします。Windowsへ通過・送信済みのAltは追加押下と解放をそのまま通し、押し直しを抑止したまま復旧判定が進むことを防ぎます。古い内部状態が残っている間の最初の押し直しは通常のAlt操作になり、IME切り替えは送りません。内部状態の解除後は通常の単独Alt判定に戻ります。意図的に押下を抑止しているAltのキーリピートは、従来どおり抑止します。

状態確認は入力中のデスクトップ上で、前面アプリへのアクセス権を確認できる場合だけ行います。前面ウィンドウの変更、取得不能、2.5秒を超える観測間隔、キー送信中は連続確認をやり直します。Alt単独の長押し判定やEmacs操作のためにアプリが意図的に押下を抑止している場合は、この復旧の対象にしません。

Emacsショートカット判定でも、Windowsへ渡したAltはWindows側の押下状態を確認します。操作後のAlt再送信も、押下中と確認できるものだけに限定します。これにより、内部に残ったAlt状態だけを根拠に通常の文字をAltショートカットへ変換したり、解放済みのAltを再び押下したりすることを防ぎます。

取得失敗と解放状態が同じ戻り値になる点、およびキーイベント処理中には非同期状態がまだ更新されていない点は、Microsoftの [GetAsyncKeyState](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-getasynckeystate) と [LowLevelKeyboardProc](https://learn.microsoft.com/windows/win32/winmsg/lowlevelkeyboardproc) の仕様に基づきます。復旧の連続確認はキーのコールバック内ではなく、フック処理スレッドのタイマーで行います。

前面ウィンドウが日本語レイアウト（LANGID `0x0411`）の場合、IMEの半角・全角指定用の仮想キー `VK_DBE_SBCSCHAR`（`0xF3`）・`VK_DBE_DBCSCHAR`（`0xF4`）は押下中の通常キーとして扱いません。Windows側にこの状態が残っていても、Alt単独操作・Emacs用Ctrl保留・無入力時のフック再登録を妨げないようにします。これらのイベント自体は抑止せず、そのまま通します。物理キーボードのF3・F4とは異なります。同じ値がOEMキーにも割り当てられているため、日本語以外またはレイアウト取得不能の場合は従来の判定を保ちます。

## ビルドと実行

```powershell
dotnet build .\AltHenkan.sln
dotnet run --project .\tests\AltHenkan.LogicTests\AltHenkan.LogicTests.csproj
dotnet run --project .\src\AltHenkan\AltHenkan.csproj
```

Windows フックの登録・解除・無入力時の自動再登録も検証する場合は、`dotnet run --project .\tests\AltHenkan.LogicTests\AltHenkan.LogicTests.csproj -- --native-hooks` を実行します。検証用フックは無効状態で入力を通過させ、キー入力は送信しません。自動再登録の検証中はキーやマウスを操作しないでください。

### リリースビルドとインストーラー

必要なもの: .NET 8 SDK 以降。インストーラーの作成には Inno Setup 6、署名には Windows SDK の signtool.exe。

```powershell
# uiAccess マニフェスト付きの自己完結・単一ファイル publish
# (src\AltHenkan\bin\Release\net8.0-windows\win-x64\publish\AltHenkan.exe。署名して Program Files 配下に置いたときだけ起動できる)
.\scripts\build-release.ps1

# 署名付きリリースインストーラー(installer_output\AltHenkan_Setup_<version>.exe)
$env:CODESIGN_CERT = "<拇印 | サブジェクト名 | path\to\cert.pfx>"
$env:CODESIGN_PASSWORD = "<pfx のパスワード。.pfx のときのみ>"      # 任意
$env:CODESIGN_TIMESTAMP_URL = "http://timestamp.digicert.com"     # 任意(既定値)
.\scripts\build-installer.ps1 -Sign

# uiAccess なし・署名なしのユーザー単位インストーラー(管理者権限のウィンドウでは動作しない)
.\scripts\build-installer.ps1 -NoUiAccess
```

| オプション | 効果 |
|---|---|
| `-Sign` | signtool で AltHenkan.exe に署名し、Inno Setup でインストーラーとアンインストーラーにも署名する。`-NoUiAccess` を付けない限り必須。 |
| `-NoUiAccess` | uiAccess マニフェストなしの実行ファイルと、ユーザー単位のインストーラーを作る。署名は任意。 |
| `-SkipPublish` | `build-release.ps1` を実行せず、既存の publish 出力を使う。 |

`-Sign` と `-NoUiAccess` のどちらも指定しない場合は、署名の必要性と実行例を表示し、例外を出さずに終了します。ビルド・署名・インストーラー作成は行いません。

たとえば、オプションなしで実行すると次の案内が表示されます。

```text
インストーラーの作成は行いません。既定のuiAccess版は、署名なしでは起動できません。
署名付きで作成する場合： .\scripts\build-installer.ps1 -Sign
署名なしで作成する場合： .\scripts\build-installer.ps1 -NoUiAccess
※ -NoUiAccess版は、管理者権限のアプリではキー変換を使えません。
```

署名付きで作成する場合は `CODESIGN_CERT` を設定して `-Sign` を指定してください。署名なしで作成する場合は `-NoUiAccess` を指定してください。オプション不足時の案内表示だけが例外なしで終了する対象で、証明書の設定不備やビルド・署名の失敗などは引き続きエラーとして報告します。

アイコン(`src/AltHenkan/AltHenkan.ico`)は `python scripts\make-icon.py` で再生成できます(Pillow が必要)。

## 診断

通常起動・サインイン時の自動起動でも、`%LOCALAPPDATA%\AltHenkan\AltHenkan-diagnostics.log` に診断情報を記録します。特別な起動オプションは不要です。再起動時は追記し、起動ごとの識別子・バージョン・プロセスIDと終了記録で区別します。

現在のログは最大1 MiBで、容量に達すると `.log.1`（直前）から `.log.4`（最古）までの4世代に移します。新規に記録するログの合計は最大5 MiBです。旧版が作成した1 MiB以上のログがある場合は、初回の移行時に内容を切り捨てず退避するため、その世代が入れ替わるまでは上限を超える場合があります。容量を超える単一の長い記録は切り詰めます。

通常ログにはフックの登録・エラー・モード変更に加え、30秒ごとに以下を記録します。フックの再登録が操作途中の判定で延期されている場合も、状態の記録は継続します。

- キーボード／マウスのコールバック回数、入力を抑止したイベント数、入力送信の失敗回数
- 左右Ctrl・Altの内部保持状態、Windowsから取得したCtrl・Altの状態、Emacsが保持するキーの個数
- 再登録要求の有無、前回の再登録からの経過時間、ログキューの省略件数
- 前面ウィンドウのキーボードレイアウト、IME半角・全角指定イベントの通過回数（`imeWidthEvents`）、`0xF3`・`0xF4` のWindows側の状態（`asyncWidth`）と内部保持状態（`trackedWidth`）。いずれも半角・全角の順
- Alt保持状態の復旧回数（`altStateRecoveries`）。復旧した時点では `Recovered released Left/Right Alt` として、保持状態と経過時間も記録
- キー送信処理の呼び出し回数（`injectionCalls`）、記録時点の送信処理の深さ（`injectionDepth`）、最大深さ（`maxInjectionDepth`）、送信処理中に呼ばれたキーボードフックの回数（`keyboardCallbacksDuringInjection`）
- Alt復旧確認の呼び出し回数（`altReconcileChecks`）、送信処理中のため確認を除外した回数（`altReconcileInjectionSkips`）、そのうち内部でAltを保持していた回数（`altReconcileInjectionSkipsWithAlt`）、除外時の最大深さ（`maxAltReconcileInjectionDepth`）

回数と最大深さは起動からの累計で、フック再登録ではリセットしません。終了時にも記録します。`altReconcileInjectionSkips` が増えれば、送信中の除外処理が実際に働いた証拠になります。`keyboardCallbacksDuringInjection` だけが増えても、復旧タイマーの再入を示すものではありません。除外回数が0でも、その記録期間中に観測されなかったことを示すだけで、除外処理が不要とは断定できません。送信の深さはラッパー処理の実行中を表し、Windowsでの入力処理完了を表すものではありません。

`leftAlt`・`rightAlt`・`leftCtrl`・`rightCtrl` の3値は「内部で押下中／元の押下イベントを通過済み／押下イベントをアプリから送信済み」の順です。Windowsから取得した状態は物理キーの押下を直接証明するものではありません。フックの処理スレッド自体が停止した場合は、このスレッド上の定期記録も停止します。

入力イベントの経緯は、通常起動でも同じフォルダーの `AltHenkan-diagnostics.log.input` に継続して保存します。1ファイル最大4 MiB、`.input.1`～`.input.4` の4世代と合わせて最大20 MiBです。次の観測点で内部状態を記録します。

- キーボードフックの入口・出口。左右Ctrl／Alt、Shift、Windows、CapsLockを区別し、その他のキーはBackspaceも含めてすべて `Other` として押下・解放だけを記録
- Ctrl／Altの保留から送信済みへの変更、EmacsでのCtrl消費、ナビゲーション入力の送信前後
- マウスボタン・ホイールの処理前後。修飾キーの送信につながる操作を対象とし、移動座標は記録しない
- 合成入力の送信開始・各送信項目・送信終了。要求件数、実際の送信件数、エラー値、自前入力のフック観測を記録
- 設定変更、無効化、サスペンド、ロック、終了、フック再登録、状態リセットの前後

`obs` はフック観測ID、`parent` は再入元、`batch` は送信ID、`parentBatch` は再入元の送信IDです。64ビットでは送信項目ごとの `token` を入力の上位32ビットに付け、自前入力の観測と直接対応させます。下位32ビットは従来の自前入力マーカーを維持します。32ビット、または上位ビットが保持されなかった場合は `token=0` となり、項目単位の対応はできませんが自前入力の判定は維持します。トークンは32ビットで循環するため、同じセッションの近接した記録で照合します。送信完了後に届く観測もトークンで対応付けます。`own=False` でもWindowsの注入フラグが立つ場合は他の注入入力として区別できますが、発行元のアプリまでは特定できません。

各行に連番 `seq` と単調増加時計 `qpc` を付け、イベントの種類に必要な項目を保存します。セッションID・形式番号 `schema=2`・バージョン・開始時のUTC／QPCと周波数は、ローテーション後も各ファイルの見出しに残します。イベント時刻は `見出しutc + (イベントqpc - 見出しqpc) / frequency` で換算でき、途中の時計調整には追従しません。通常ログの `traceSession`／`traceSeq` は、対応する入力イベントログの状態記録を指します。省略された記録を指す場合や、観測停止中で `traceSeq=0` の場合もあります。`Status` には状態記録の理由とキーボード・マウスの呼び出し回数を残します。呼び出しが増えないことだけでは、フック停止と単なる無入力は区別できません。

前面ウィンドウのハンドル・プロセスID・スレッドIDも入口で取得します。通常入力のキーコード・スキャンコード・文字・ウィンドウタイトルは保存しません。`sentScan`／`sentVk` はアプリ自身が生成した入力だけを表します。打鍵回数・時刻・拡張キーのフラグは残り、合成入力からEmacs操作を推定できる場合もあります。通常キーの匿名化は、こうした操作情報まで除去するものではありません。

`state` は内部状態のビット列です。下位から4ビットずつ、左Ctrl・右Ctrl・左Alt・右Altについて「押下中／元の押下を通過済み／押下を送信済み／Emacsで消費済み」を表します。ビット16・17は左右AltのShift保留、18はEmacsモード、19はCapsLock捕捉中、20・21はアプリ・Emacs機能の有効設定です。`captured` はEmacsの保持キー数、`nonAltKeys` は通常キーの内部保持数です。Ctrlを通過させた理由は、保留対象外の `ControlNativeNotDeferrable` と、他の入力を検出した `ControlNativeOtherInput` に分けます。`asyncRaw` のビット0～5はWindowsから取得した左Ctrl・右Ctrl・左Alt・右Alt・Shift・Windowsキーの状態です。取得不能と解放はこの値だけでは区別できず、フック入口では現在イベントの反映前です。送信項目を示す `SendItem` では状態取得を繰り返しません。

`Settings` は起動時と設定変更の前後に記録します。`settings` のビット0～1はCtrlの左右指定、2～3はAltの左右指定（0=両方、1=左、2=右）、4はEmacs初期モード、5・6は左右Altの長押し有効設定です。`longPressMs` は長押し閾値、`shortcuts` は有効なEmacs操作のビット列で、下位からControlB、ControlF、ControlP、ControlN、ControlA、ControlE、AltB、AltF、ControlD、ControlK、AltLess、AltGreater、AltDの順です。これらは設定内容であり、実際に入力した文字列ではありません。

`verdict=Forwarded` はアプリが次のフックへ渡したこと、`Suppressed` はアプリが抑止したことを表します。`result` は通過時には後続フックの戻り値、抑止時にはアプリ自身の戻り値です。受信アプリへの到達は証明しません。`verdict=Exception` の場合はコア処理が完了しておらず、その行の `result` は判定に使用できません。例外後の転送は同じ `obs` の `Fallback` に記録し、`index=0` が転送前、`index=1` が転送後の戻り値です。`SendEnd` の `index=1` は送信APIが戻ったこと、`index=0` は例外などで戻らなかったことを示します。APIの送信件数とフックでの観測件数も、受信アプリでの処理完了とは区別します。終了時には `Unregistered` としてフック解除処理後の状態を記録しますが、それだけで利用者の入力が回復したとは判断できません。

文字列化とファイル操作は別スレッドで行い、フック内では観測値を取得し、最大8192件のキューへ追加します。250ミリ秒間隔を目安に書き出すため、フックの定期処理や終了操作を待たずに記録が残ります。キューが満杯なら待機せず省略し、`Trace gap` と通常ログの `traceDropped` に件数を残します。記録取得の例外は `traceRecordFailures`、現在の書き込み失敗は `traceWriteError` で確認できます。

書き込み失敗時は、通常ログへ例外の詳細を記録し、イベント観測を停止して1秒間隔でファイルを開き直します。再開時に `Trace outage` として観測停止区間を残します。停止中の入力数や書き出し前のバッファの損失は数えられないため、`traceDropped` だけで全欠落数は分かりません。通常終了では最大2秒の排出待ちを行い、時間切れや保存できなかった待機中の記録も通常ログに通知します。通常ログ側も書けない場合は通知を保存できません。強制終了・ディスク障害などで未保存の記録が失われる場合があり、欠落区間のイベントが起きなかったとは判断できません。

入力できなくなった場合は、可能なら発生時刻を控えて通知領域から終了し、作業を再開する前に通常ログと入力イベントログ、それぞれの `.1`～`.4` を別フォルダーへコピーしてください。再起動しても直ちには消えませんが、稼働が続くと古い世代は入れ替わります。保存期間は入力の頻度で変わり、一定時間分の保存は保証しません。

Alt・Emacsの各操作と送信イベントまで詳しく調べる場合は、起動中の Alt Henkan を終了し、`--diagnostics` を付けて起動してください。ソースから起動する場合:

```powershell
dotnet run --project .\src\AltHenkan\AltHenkan.csproj --configuration Release -- --diagnostics
```

インストール済みの場合:

```powershell
Start-Process "C:\Program Files\AltHenkan\AltHenkan.exe" -ArgumentList "--diagnostics"
```

詳細ログも同じ容量・世代制限に従うため、通常ログより早く世代が入れ替わります。どちらのモードでも、通常入力の文字、ウィンドウのタイトル、クリップボードの内容は記録しません。

フックの再登録世代・コールバック回数・遅いコールバックも記録します。ログ書き込みは容量制限付き非同期キューを使用し、ディスクが遅い場合はログを省略して入力処理を優先します。ログファイルへ書き込めない場合もアプリの入力処理は継続します。

### キー解放通知の欠落を再現するテスト

入力イベントログのテストでは、保存途中の例外と再開、排出待ちの時間切れ、ローテーション後の見出し、設定・サスペンド・ロック・終了の記録、記録有効／無効での入力動作の一致、送信完了後に遅れて届く自前入力の対応付けも検証します。

`--native-input-marker` は追加の明示オプションです。F24の押下・解放をWindowsへ送り、テスト専用フックで対象の自前入力を観測・抑止して、マーカーの往復を検証します。通常テストと `--native-hooks` だけではこの送信は行いません。この検証は実行した環境でのマーカーの保持を確認するもので、入力異常の再現や他の環境での動作を保証するものではありません。

通常のロジックテストには、Emacs操作のキー解放を意図的に省き、後続の単独キーが抑止される条件、Ctrlの内部押下状態が残る条件、CapsLockの解放が欠ける条件を含めています。実際の状態クラスと再登録判定を使い、無入力が長く続いても保持状態によって再登録が延期される現行動作を確認します。実際のWindowsへのキー送信やフック登録は行いません。

これらは問題の条件を固定する再現テストで、Ctrl・Alt・Emacsのキー解放通知の欠落全般から復旧済みであることを示すテストではありません。Windows全体で入力不能になった報告と同じ原因かどうかは未確定です。

Altの押し直しテストでは、実際のAltイベント処理と復旧処理を呼び、次のフックへの受け渡しだけを模擬処理に置き換えています。左右Altについて、最初の状態確認前／確認後の押し直し、通常のキーリピート、抑止中の長押し、押下から解放までの状態遷移を確認します。Windows側の押下状態は模擬しており、実際のキー入力は送信しません。

2026年10月11日のログでは、Windowsへ押下を送信済みの左Altが内部に残り、Windows側の解放状態と食い違う記録を確認しました。この条件の復旧と再送信抑止を回帰テストに追加しています。左右Alt、通常／抑止中の長押し、権限などによる取得不能、前面切り替え、観測の途切れ、キー送信中を対照条件とし、`--native-hooks` では実際のサービスにも状態を与えて復旧を検証します。テストでキー入力は送信しません。食い違いが最初に生じた理由や、Windows側も押下状態のままになる場合、抑止中Alt・Ctrl・Emacsのキー解放欠落全般は引き続き確認対象です。

別途、IMEの半角・全角指定用の仮想キーだけが押下状態で残る条件に対する回帰テストを追加しています。日本語レイアウトでは同時押し・フック再登録待機の対象から除外し、通常キー・修飾キー・マウスボタンが押されている場合や、日本語以外のレイアウトでは従来の保護が働くことを確認します。`--native-hooks` の検証では実際の `0xF3` の状態も表示しますが、自然発生したAlt切り替え不能やIME切り替えの実機確認を代替するものではありません。

## 制限事項

- 署名付きの uiAccess ビルド(「管理者権限のウィンドウについて」を参照)でない場合、より高い整合性レベルで動作しているアプリが前面にある間は、Windows によって入力の監視も送信も遮断されます。
- キーボードフックはセキュアデスクトップ(UAC の同意画面など)では動作しません。
- `VK_IME_ON` / `VK_IME_OFF` は Microsoft IME で対応しています。他社製 IME での対応は未確認です。
